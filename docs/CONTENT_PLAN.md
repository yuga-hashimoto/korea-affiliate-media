# コンテンツ再編計画（2026-11-10）

## 0. 前提（実測）

- Search Console（2026/11/9時点）: インデックス登録17 / 未登録66。うち「クロール済み - インデックス未登録」が **58ページ**（初検出 2026/11/7）。
- 公開記事38本の本文は**中央値315字**（範囲: 232〜439字）。見出しは3〜4個。
- 検索流入は直近7日でクリック1・表示3（データは11/7まで）。実質ゼロ。
- つまり「ページ数不足」ではなく「1ページあたりの情報量と独自性の不足」が原因。記事を増やすほど薄いページが増え、評価は下がる。

## 1. 方針

1. **薄い記事を統合してページ数を減らし、1ページあたりの情報量を上げる**（今回実施）。
2. **統合後の記事に、一次情報で確認した具体情報を足して3,000字級にする**（次フェーズ）。
3. 新規記事は「検索意図が明確なロングテール」に限定し、1本ずつ公開・インデックス確認する。
4. 量産しない。記事数より「インデックス率・表示回数」をKPIにする。

### 統合のルール
- 既存のレビュー済み本文のみを統合し、新しい事実は追加しない（今回の統合分）。
- 統合元URLは `public/_redirects` で308転送し、404を作らない。
- タイトル・説明・タグは統合後の検索意図に合わせて付け直す。

### 記事を書くときの条件
- 一次情報（観光公社・空港・鉄道・公的機関・事業者公式）で確認し、出典URLと確認日時を記事に残す。
- 営業時間・料金・運行状況は「変更される前提」で書き、公式確認を促す。
- 体験談・現地取材を装わない（`AGENTS.md`）。
- AIが書いた記事は `status: "review"` で保存し、人のレビュー後に `published` にする。

## 4. 公開・検証の手順

1. 記事を `review` で作成 → 人がレビュー（事実・表現・出典）→ `published`。
2. ビルド・unit/E2E・`pnpm jobs:quality` を通す。
3. デプロイ後、Search ConsoleでURL検査 →「インデックス登録をリクエスト」。
4. 1〜2週間後にGSCで「クロール済み - インデックス未登録」の減少を確認。
5. インデックスされない記事は、リライト → 統合 → 転送の順で整理する。
